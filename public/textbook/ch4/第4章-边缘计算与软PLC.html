章节导言 ​

前三章我们学习了设备之间的通信协议（第 3 章）和工业互联网的整体架构（第 2 章）。现在，数据已经从设备中采出来了——接下来怎么办？

直觉上的答案是"传到云端"。云端算力强、存储大、算法新，把数据送过去分析似乎理所当然。但这个直觉在工业场景中会遇到三个现实障碍：数据量太大导致通信成本高到不划算、网络延迟导致云端来不及做实时决策、以及网络本身不总是连通的。

这一章要讲的技术——边缘计算——就是解决这三个问题的。它的思路很简单：数据在哪产生，就在哪先做处理。有价值的数据才上传，没价值的数据在本地过滤掉；需要毫秒级响应的决策在本地立即执行，不需要等云端的往返延迟；断网时设备继续自主运行，恢复后再同步。

你还会在这一章里亲手触及一个"跨界"概念——软 PLC。它让"控制"和"计算"在同一台设备上融合，是边缘计算在工业控制领域最典型的落地形态。

环境确认：本章实践基于第 3 章已安装的 Node-RED + Modbus 节点，新增安装 OpenPLC。请确认 Node-RED 可访问、Modbus 节点已安装。

4.1 数据都往云端传，行得通吗？——算一笔账 ​

4.1.1 海上风电场的带宽账单 ​

某海上风电场安装了 100 台风机。每台风机上装了 150 个传感器——振动、温度、风速、油压、电流、电压……每个传感器每秒采集 50 次数据。也就是说，整个风电场每秒产生：

100 × 150 × 50 = 750,000 个数据点/秒
1

假设每个数据点占用 8 字节（时间戳+数值+标签），一天的原始数据量是：

750,000 × 8 × 86,400 ≈ 5.18 × 10¹¹ 字节 ≈ 500 GB/天
1

500 GB 是什么概念？相当于你每天要用掉一部 512GB 手机的全部存储空间。而这类数据不是存下来就完了——它需要通过卫星通信链路实时传回岸上的数据中心。卫星通信按数据量计费，一天的传输成本就可能高达数万元。而且卫星链路延迟通常在 500ms 以上，云端下发控制指令再回来，至少 1 秒——风机偏航控制根本来不及响应。

4.1.2 四大驱动力倒逼边缘计算 [1] ​

驱动力痛点边缘计算对策典型场景
省带宽/省钱海量原始数据上传成本高本地过滤、压缩、只传增量/异常/摘要风电、油田、远程站点
低延迟/快云端往返 100-500ms，控制回路跟不上本地毫秒级决策、闭环控制视觉检测、机器人协同、偏航控制
断网自治/稳网络不可靠、甚至长时间离线本地缓存、自主运行、来网补传地铁隧道、矿井、海上平台
数据隐私/密工艺参数、配方、产能属商业机密敏感数据不出厂、本地脱敏/加密核心工序、军工、医药

一句话记住：边缘管"现在"(实时判断)，平台管"趋势"(历史分析)——边缘网关每秒做一次温度判断，但无法回答"过去半年这台设备的振动趋势是否在恶化"，这需要平台侧的海量历史数据和机器学习模型。

4.3 边缘计算三种典型工作模式 ​

模式核心逻辑典型场景数据流向
数据预处理清洗、去噪、单位换算、格式统一、聚合采集频率高、原始数据脏、上传带宽贵设备→网关(清洗/聚合)→云端(存摘要)
本地决策规则引擎/阈值/简单模型在边缘直接触发动作毫秒级响应、断网自治、安全联锁设备→网关(判断/执行)→执行器；同步上传结果

工程经验：实际项目中三种模式混合使用——同一网关上，温度做阈值报警(本地决策)，振动做均值上传(筛选上传)，原始波形按需回传(预处理)。

4.4 走近软 PLC：当控制变成软件 ​

4.4.1 硬 PLC vs 软 PLC vs 安全 PLC [4] ​

维度硬 PLC (传统)软 PLC (SoftPLC)安全 PLC (Safety PLC)
形态专用硬件盒子(西门子 S7、三菱 FX、欧姆龙 CJ)通用工控机上运行的软件进程经 SIL/PL 认证的专用硬件
操作系统厂商定制实时 OS (VxWorks, RTOS)通用 Linux/Windows + 实时补丁安全认证 RTOS
编程环境厂商专用 (TIA Portal, GX Works, Sysmac)Codesys、TwinCAT、OpenPLC、Python/C++厂商专用安全编程软件
通信协议自家总线+标准以太网标准以太网(ProfiNet/EtherCAT/Modbus/OPC UA)安全总线 + 标准以太网
优势极高稳定性、10年不重启、抗干扰强灵活、可移植、控制+计算融合、成本低SIL 3/PL e 级安全、失效安全
局限厂商锁定、扩展难、不擅长数据分析实时性略弱、非安全关键、需硬件加固编程受限、昂贵、仅做安全

类比：硬 PLC = 固定电话（只能打电话，极稳）；软 PLC = 平板电脑（能打电话、还能拍照、导航、装 App）；安全 PLC = 防爆对讲机（关键时刻救命，功能单一但绝对可靠）。

[图4-5 硬PLC/软PLC/安全PLC 对比图]

4.4.2 为什么软 PLC 属于边缘计算？ ​

  • 物理形态 = 边缘侧一台工控机 + 一个软件进程
  • 同一设备上：软 PLC 进程控制传送带启停，Node-RED 进程采集振动分析健康状态
  • 控制与计算不再分家——传统硬 PLC 做控制不擅长分析，云端做分析延迟太高不适合控制，软 PLC 在边缘把两者融合

4.4.3 明确边界：软 PLC ≠ 安全 PLC ​

重要：软 PLC 管"干活"，安全 PLC 管"保命"，两者各司其职，不可互相替代。

  • 急停按钮回路、安全光幕联锁、防护门互锁 → 必须用硬件安全 PLC/安全继电器
  • 依据：IEC 61508 (SIL 1-4) / ISO 13849 (PL a-e) [3]
  • 软 PLC 解决"控制逻辑软件化"，安全功能有独立国际标准，要求硬件级失效安全

4.5 实践 1：用 Node-RED 构建边缘数据处理流（3 课时） ​

场景：模拟一台电机的边缘监控系统。温度+振动传感器每秒 1 组读数。边缘网关职责：

  1. 实时判断温度 > 80℃ → 本地触发报警
  2. 计算最近 10 秒滑动均值（消除瞬时噪声）
  3. 正常情况下每 30 秒上传 1 次均值摘要给"云端"(Debug 模拟)
  4. 振动出现异常尖峰(>3mm/s) → 打包上传原始数据

任务一：传感器模拟 ​

拖 Inject(1秒间隔) → Function 电机传感器模拟：

javascript
// 模拟电机温度和振动传感器
var temp = 55 + Math.random() * 30;    // 55-85℃
var vib  = 0.5 + Math.random() * 3.5;  // 0.5-4.0 mm/s
// 5%概率制造高温，3%概率制造高振动
if (Math.random() < 0.05) temp = 85 + Math.random() * 10;
if (Math.random() < 0.03) vib  = 4 + Math.random() * 3;
msg.payload = { temperature: Math.round(temp * 10) / 10, vibration: Math.round(vib * 100) / 100 };
return msg;

任务三：滑动均值计算（核心：context 状态保持） ​

拖 Function 计算10秒滑动均值(每30秒输出)：

javascript
// context 是 Node-RED 给每个节点的"笔记本"，跨调用持久化
context.dataBuffer = context.dataBuffer || [];
context.dataBuffer.push(msg.payload);
if (context.dataBuffer.length > 10) context.dataBuffer.shift();

context.counter = context.counter || 0;
context.counter++;
if (context.counter < 30) return null;  // 不输出，积累
context.counter = 0;

var sumTemp = 0, sumVib = 0;
context.dataBuffer.forEach(d => { sumTemp += d.temperature; sumVib += d.vibration; });

msg.payload = {
    avgTemperature: Math.round(sumTemp / 10 * 10) / 10,
    avgVibration: Math.round(sumVib / 10 * 100) / 100,
    sampleCount: 10,
    latestRaw: context.dataBuffer[9]
};
return msg;

任务二：在 OpenPLC 编写简单程序 ​

小科普：ST 是什么？ ST（Structured Text，结构化文本）是 IEC 61131-3 国际标准规定的 PLC 编程语言之一，用类似高级语言（C/JavaScript）的文字来写控制逻辑——IF ... THEN ... ELSE、赋值、计数等。这是本书第一次出现 ST，你不需要精通，照着示例理解含义、照抄运行即可；想深入 PLC 编程时再系统学习。

(* 简单温度报警逻辑 *)

    Alarm := TRUE;
ELSE

(* 计数器 *)

任务三：Node-RED 通过 ModbusTCP 读写 OpenPLC ​

在 Node-RED 新建 Flow：

  • Modbus Read (FC4 读输入寄存器 0-1) → 解析 REAL → Gauge 显示温度
  • Modbus Read (FC1 读线圈 0) → LED 显示报警状态
  • Modbus Read (FC3 读保持寄存器 10-11) → Text 显示计数器
  • Inject(手动) → Function 构造温度值 → Modbus Write (FC16 写输入寄存器 0-1) → 模拟传感器写入

部署 → 打开 OpenPLC Web 监控变量 → 观察 Node-RED 仪表盘同步变化 → 体会"软 PLC 控制 + Node-RED 可视化"同机共存。

核心体会：同一台 Ubuntu 上，OpenPLC 进程跑控制逻辑，Node-RED 进程跑采集/可视化/边缘计算，控制与计算融合在边缘侧——这就是软 PLC 作为边缘计算典型形态的意义。

本章小结 ​

本章我们从风电场 500GB/天的带宽账单出发，确立了边缘计算的四大驱动力（省、快、稳、密）与三层架构（网关/服务器/云端），理清了与 ISA-95、IIRA 的模型映射。我们理解了数据预处理、本地决策、数据筛选上传三种典型工作模式，并深入剖析了软 PLC作为"控制+计算融合"的边缘计算核心形态——区别于硬 PLC 的厂商锁定、区别于安全 PLC 的功能边界。

在实践中，我们用 Node-RED 完整构建了一个边缘数据处理流：模拟传感器→阈值实时报警→滑动均值(context 状态保持)→计数器控制上传频率→振动异常原始数据回传，实测数据量减少约 85%。我们还安装了 OpenPLC，体验了在同一台设备上"软 PLC 跑控制、Node-RED 跑计算"的协同——这是边缘计算落地工业控制的最真实形态。

衔接提示：第 5 章我们将把视角拉到云端/平台层——边缘筛选后的数据上传到平台，用什么技术存储、管理、部署应用？答案是 Docker 容器化与工业互联网平台三层能力。

思考与练习 ​

思考题 ​

  1. 某工厂有 50 台设备，每台 100 个传感器，每秒 10 次采集。若全量上传云端，日数据量约多少 GB？若边缘只上传异常(1%)和分钟级均值，压缩比约多少？

  2. 边缘网关和边缘服务器的关键区别是什么？各自适合跑什么任务？为什么说边缘网关是"实际部署最多的边缘形态"？

  3. 软 PLC 和硬 PLC 的根本区别是什么？什么场景下必须用硬件安全 PLC 而不能用软 PLC？为什么？

  4. Node-RED Function 节点中为什么要用 context 而不用普通变量？context.dataBuffer 和 var dataBuffer 有什么本质不同？

  5. 举一个你日常生活中的"边缘计算"例子。手机语音助手的"唤醒词"是在手机本地检测的还是在云端检测的？如果是本地检测，为什么这样设计？

选择题 ​

  1. 以下哪项不是边缘计算的核心驱动力？ A. 降低带宽成本　B. 减少网络延迟　C. 替代所有云计算功能　D. 保障离线时本地自治

  2. 边缘网关在边缘计算架构中通常部署在什么位置？ A. 云端数据中心　B. 靠近现场设备的车间或机柜内　C. 总部 ERP 机房　D. 运营商的基站

  3. 软 PLC 与传统硬 PLC 的根本区别在于？ A. 软 PLC 不能执行梯形图程序 B. 软 PLC 的控制逻辑以纯软件形式运行在通用工控机上 C. 软 PLC 不需要传感器输入 D. 软 PLC 只能用于娱乐，不能用于工业

  4. Node-RED 中的 Function 节点使用哪种编程语言？ A. Python　B. C++　C. JavaScript　D. 梯形图

  5. 滑动均值的计算在边缘数据处理中的主要作用是？ A. 增加数据量　B. 消除传感器读数的瞬时随机噪声　C. 加密数据　D. 改变数据单位

  6. OpenPLC 默认使用什么协议与外部系统通信？ A. ProfiNet　B. EtherCAT　C. ModbusTCP　D. CC-Link IE

  7. 边缘计算中，"边缘执行→云端训练→模型下发→边缘更准"描述的是？ A. 边缘和云的竞争关系　B. 边缘和云的互补协同关系　C. 边缘完全取代云的过程　D. 一种数据加密算法

判断题 ​

  1. （ ）边缘计算意味着所有数据都必须在本地处理，永远不能上传到云端。
  2. （ ）边缘服务器通常比边缘网关拥有更强的算力，适合运行 AI 推理等计算密集型任务。
  3. （ ）硬 PLC 运行的是厂商定制的高稳定实时操作系统，而软 PLC 把控制逻辑做成了通用工控机上的软件。
  4. （ ）Node-RED 的 Switch 节点可以根据消息的某个字段值决定消息走向哪个分支。
  5. （ ）OpenPLC 是西门子公司的商业软 PLC 产品，需要购买许可证。
  6. （ ）边缘网关在断网时可以将数据缓存在本地，等网络恢复后再补传到云端。
  7. （ ）ModbusTCP 协议在 OpenPLC 和 Node-RED 之间充当了数据传输的"通用语言"。

习题答案 ​

选择题答案：1-C　2-B　3-B　4-C　5-B　6-C　7-B

简要解析：① 边缘不替代云，而是与云互补，C 错；② 边缘网关部署在靠近现场设备的车间/机柜；③ 软 PLC=通用工控机上的纯软件进程；④ Function 节点用 JavaScript；⑤ 滑动均值用于消除瞬时随机噪声；⑥ OpenPLC 默认用 ModbusTCP 对外通信；⑦ 边缘执行→云端训练→模型下发 描述的是边缘-云互补协同。

判断题答案： 1.（×）边缘计算"该本地处理的本地处理、该上传的上传"，不是所有数据永留本地。 2.（√）边缘服务器算力比网关强，适合 AI 推理等计算密集任务。 3.（√）硬 PLC 跑厂商定制实时 OS，软 PLC 把控制逻辑做成通用工控机上的软件。 4.（√）Switch 节点按字段值（如 msg.payload.temperature）分流到不同分支。 5.（×）OpenPLC 是开源免费软 PLC（Thiago Alves 发起），非西门子商业产品。 6.（√）边缘网关断网可本地缓存，恢复后补传（断网自治）。 7.（√）ModbusTCP 是 OpenPLC 与 Node-RED 之间的"通用语言"。

思考题参考要点：

  1. 估算：50 台 × 100 传感器 × 10 次/秒 × 86400 秒 = 43.2 亿点/天；按 8 字节/点约 34.6 GB/天。若只上传 1% 异常 + 分钟级均值，压缩比可达数十倍~百倍级。
  2. 网关：低算力（1-4 核 ARM）、贴近设备、<10ms，做协议解析/清洗/阈值/缓存；服务器：高算力（GPU）、做 AI 推理/多流融合/本地训练。网关"实际部署最多"——数量大、便宜、贴近现场，是边缘计算的主力形态。
  3. 软 PLC=通用工控机+软件（灵活/可移植/控制+计算融合），硬 PLC=专用硬件+定制实时 OS（稳定/抗干扰/厂商锁定）。急停、安全光幕联锁等安全关键场景必须用硬件安全 PLC/安全继电器（IEC 61508/ISO 13849 失效安全要求）。
  4. context 是 Node-RED 给节点的跨调用"笔记本"，能跨消息持久保存；普通 var 每次函数调用都重置。要跨调用计数/缓存（如滑动均值缓冲区）必须用 context。
  5. 唤醒词（"嘿 Siri"）在手机本地检测：本地毫秒级响应、断网可用、不用把音频都传云端（省流量+隐私）。这正是"数据就近处理"的边缘计算思想在日常生活的例子。
